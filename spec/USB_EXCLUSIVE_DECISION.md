# Windows 全应用 USB 独占：真实方案对比与决策（v2）

2026-10-17，应用户要求重新调研。用户核心质疑（完全成立）：**Steam 虚拟声卡转接是“假独占”，音质不如系统共享输出，不能算数**。本文给出劣化机理、可选方案、风险评估与推荐路线。约束：**绝不高风险方案**（此前音频链路被搞崩过一次：快速采样率轮换后持续异响直到重启）。

## 一、为什么 Steam 转接音质差（劣化机理，已实测）

现在的“独占”链路是：全应用 → Steam Streaming Speakers（共享混音）→ WASAPI 回环采集（实测 192 kHz float）→ **WDL 重采样器 192k→48k + 双时钟伺服** → WASAPI 独占 USB。劣化来自四处：

1. **重采样**：192 kHz 采集必然被降采样到输出采样率。离线理想测量（256 taps/256 phases）残留 −114 dB，但这只是理想值。
2. **双时钟伺服**：Steam 虚拟驱动的“时钟”和 USB 晶振是两套时钟，`ClockedResampler` 的伺服以 ppm 级持续微调比率（实测 0.1→3.7 ppm 漂移中）——比率持续微动就是音质的“不对劲”。
3. **Steam 驱动本身**：它是游戏串流驱动，有自己的缓冲/混音路径，不是为音质设计。
4. 采集 192k → 输出 48k 还多一级数字滤波相位影响。

**结论：劣化的锅在“转接 + 重采样”，不在“独占/共享”本身。** VB-Audio 官方文档自己就区分两类产品（vb-audio.com/Cable）：普通 VB-Cable 可转换采样率；**Hi-Fi Cable “works like VB-CABLE except it needs to be configured with the same samplerate on its Input and Its output. HI-FI Cable is bit perfect and supports up to 24 bits 384 kHz”**——即：虚拟线缆要做到 bit perfect，必须输入/输出同采样率、不转换。

## 二、还有一个立即可用的事实（零风险）

Windows 共享混音是 float32；**当音乐采样率 = 系统混音率 = 设备格式时，全链没有任何重采样**，float32 加法对单位增益是精确的。网易云文件多为 44.1 kHz：把“同步到系统”设为 44100（4X 支持），原生 APO 模式即为**事实上的 bit-perfect 播放**，音质优于现在的 Steam 转接。缺的只是“设备独占权”（无系统提示音混入、无其他应用抢占），不是透明度。

## 三、方案对比

| 方案 | 音质 | 独占权 | 风险 | 可分发 | 工作量 |
| --- | --- | --- | --- | --- | --- |
| A. 原生 APO + 采样率对齐（现状能力） | 匹配采样率时透明/bit-perfect | 无（共享） | **零** | 是（已签名前需 EV） | 已完成 |
| B. **Hi-Fi Cable（VB-Audio 签名驱动）作入口 + OpenEQ DSP + USB 独占** | 同采样率 bit-perfect（厂方声明） | 是 | **低**（正规签名驱动安装，可卸载，不改 Secure Boot/testsigning） | 依赖第三方闭源驱动，只能作可选模式 | 中（改中继为同率直通） |
| C. **OpenEQ.VirtualCable 自研驱动 + 单时钟拉动中继** | 同 B（自己控制节拍，无重采样） | 是 | **中**（自有内核驱动加载需 test-signing+重启；出问题是蓝屏级别，但有恢复预案） | 是（MS-PL 源码衍生 + 自有构建） | 大（驱动节拍 IOCTL + 中继拉动）；构建链已通，.sys 已能编译 |
| D. Steam/网易虚拟声卡转接（现状） | **差（实测机理如上）** | 末段独占 | 低但质量不可接受 | — | **弃用** |
| E. 每应用 WASAPI 独占（播放器直连） | bit-perfect | 是（单应用） | 零 | 是 | 不解决“全应用统一 EQ” |

要点：任何“全应用”方案都必须混音；**多个不同采样率的源同时播放时，只能做到统一到一个公共采样率（其中必有转换），不可能每个源都 bit-perfect**。单音源（听音乐的典型场景）在 B/C 下 bit-perfect。

## 四、推荐路线（遵守“不高风险”约束）

1. **立刻（零风险）**：主推 A——听音乐时用原生 APO + 同步 44100（44.1k 内容）。这已经不是“半成品音质”，是透明链路。UI 文案如实标注共享属性。
2. **已实现并实测（2026-10-17 晚）**：中继链路**输出采样率自动跟随入口**，同率时彻底删除重采样器（零 ASRC）。TEARDSP 实测：入口 192 kHz → 输出 192 kHz/24-bit 独占，全链零重采样，EQ 传递精确（−41.995/−30.000 dB）、独占权严格（0x8889000A）、零溢出：`evidence/bridge-zerocopy-tearsdsp.json`。旧链路在同位置有一次 192k→48k WDL 重采样——这就是“假独占不如共享”的主要劣化源，现已消灭。不同采样率入口仍会如实标注“含重采样”。
3. **短期（低风险，达成内容采样率级真 HiFi）**：做 B。安装 VB-Audio Hi-Fi Cable（正式签名驱动，常规安装/卸载，不动系统安全设置），按其要求把输入/输出配成同一采样率（= 音乐内容采样率），中继即为全程零转换。作为可选模式保留并在许可中声明第三方驱动。
4. **中期（自主可控）**：做 C。OpenEQ.VirtualCable（构建链已通）加“外部节拍”模式 + 可设置混合采样率跟随内容。**加载决策交给用户**：需 test-signing+重启；加载前建系统还原点，恢复预案（pnputil 禁用设备 / 安全模式回退）写入安装脚本。
5. **不做**：继续用 Steam/网易虚拟声卡做质量链路（可保留作兼容模式但必须标注“转接+重采样，音质不推荐”）；不做快速采样率轮换压测；不悄悄改 BCD/重启。

## 六、安卓端真 HiFi 路线（与 Windows 同标准：零重采样、采样率跟随、单时钟）

现状：Root 全局 PEQ（临时 AudioPolicy 捕获 → 自研 DSP → AudioTrack **共享**输出）。共享输出经 AudioFlinger 混音、可能有 SRC，不是独占、不保证 bit-perfect——同 Windows 的“共享”短板。

真 HiFi 目标链：应用音频 → 系统捕获（原采样率）→ 自研 DSP → **USB DAC 独占直出（采样率跟随内容，DAC 时钟域）**。

- **首选路线（风险最低、最成熟）**：Android 内核自带 `snd-usb-audio`——USB DAC 插入后即注册为 ALSA 声卡（Z Flip5 已核实存在 ALSA 节点与系统 tinyalsa）。用 tinyalsa 按 DAC 硬件采样率直接写 PCM：内核 USB 栈负责 UAC 等时传输与反馈端点（时钟域是 DAC 自己的），应用侧不做任何重采样。采样率跟随 = 按内容采样率打开对应 hw_params（UAC2 由内核发 SET_CUR）。Root 已具备。风险纪律同 Windows：**单次单采样率验证，禁止轮换压测**。
- **备选路线**：libusb 用户态 UAC1/UAC2 等时输出（自管反馈端点/包调度）。工作量大、易踩时钟坑，仅当内核驱动不可用时才考虑；现有 libusb 模块仅是枚举基础。
- **共享配置**：Windows/安卓用同一套 JSON（已有），DSP 系数按各平台实际输出采样率重算（已有）。
- **边界照旧**：多源不同采样率同时混音时统一到公共采样率（必有转换），单音源场景全链 bit-perfect；受保护音频/offload 不承诺。

## 五、风险管控（沿用并强化）

- 任何格式变更：单次、先备份、回读确认、可恢复；禁止轮换压测。
- 驱动加载前置条件：用户明确同意 + 系统还原点 + 明确恢复命令（已在 `install-testsigning.ps1` 约定，脚本本身不改 BCD、不重启）。
- 第三方驱动（方案 B）只走正式签名渠道安装，不装测试签名第三方驱动。
- 实听验收以用户耳朵为准，数字测量只作辅助（此前教训：AudioDG 内部通过≠实听通过）。
